1. Project Overview

CourseCart is a modern, full-stack learning management application designed to streamline the process of discovering, purchasing, and managing educational courses. It provides an end-to-end digital platform enabling customers to securely register, browse courses across categories, view detailed syllabuses, simulate purchases for immediate enrollment, and access lesson content while tracking their progress.

The application strictly enforces role-based workflows for two primary user types:

  • Customers (USER): Can register, log in, browse the active course catalog, purchase single courses via simulated checkout, access purchased course content (lessons), track progress per lesson, and view their order history.
  • Administrators (ADMIN): Can log in, manage categories and courses, manage course lifecycle (Draft, Active, Inactive), manage text-based course lessons, and view basic platform reporting metrics globally.

The project is built as a microservices-based architecture using Java 21, Spring Boot, Spring Cloud, and Angular — demonstrating modern enterprise development practices at a capstone-level of complexity.

2. System Architecture

The solution follows a Microservices Architecture consisting of four business services: User Service, Catalog Service, Commerce Service, and Enrollment Service, with communication managed through Spring Cloud Gateway and Spring Cloud Consul. All frontend requests must pass through the API Gateway.

2.2 Authentication & Authorization Design

Important: CourseCart utilizes a Frontend-Managed Identity Design. Identity (Username and Role) is managed in Angular `localStorage`. No JWTs, Spring Security, or HTTP Interceptors are used to pass headers. Usernames/IDs are passed as standard explicit API parameters where required.

3. User Stories

The following fifteen user stories define the complete functional scope of the application.

US 01 – User Registration

Priority: Must Have Primary Microservice: User Service

Acceptance Criteria

  • As an anonymous visitor, I want to securely register so that I can access the CourseCart platform and purchase courses.
  • Customers shall be able to register using Full Name, Username, and Password.
  • Usernames shall be unique across the system.
  • Duplicate username registrations shall not be allowed.
  • Newly registered users shall automatically receive the role USER.
  • Mandatory fields shall be validated before registration.
  • Appropriate success, validation, and error messages shall be displayed.

US 02 – User Login

Priority: Must Have Primary Microservice: User Service

Acceptance Criteria

  • As a registered user, I want to log in so that I can access the application based on my assigned role.
  • Users shall be able to log in using their Username and Password.
  • Authentication shall be performed by validating the entered credentials directly against stored database records (plaintext for demo purposes).
  • User role shall be identified during successful login.
  • Identity and role shall be stored securely in localStorage.
  • Users shall be able to log out by clearing the active session in local storage.

US 03 – View Profile

Priority: Must Have Primary Microservice: User Service

Acceptance Criteria

  • As a logged-in user, I want to view my basic profile details, so that I can verify my account information.
  • System displays the user's name and username securely.

US 04 – Admin Category Management

Priority: Must Have Primary Microservice: Catalog Service

Acceptance Criteria

  • As an admin, I want to manage course categories, so that I can organize the catalog.
  • Admin can create a new category with a name.
  • Admin can edit an existing category name.
  • Admin can delete a category. If courses are attached to the category, the database foreign key constraint will prevent deletion. [Note: The current implementation does not have an explicit application-level guard; protection is enforced by the MySQL FK constraint. DataIntegrityViolationException is not specifically handled in GlobalExceptionHandler � this is a known gap.]
  • Appropriate validation and error handling shall be implemented.

US 05 – Admin Course Management

Priority: Must Have Primary Microservice: Catalog Service

Acceptance Criteria

  • As an admin, I want to manage course metadata, so that I can define what is sold on the platform.
  • Admin creates and edits courses (Title, Description, Price, Category, Image URL).
  • Admin can assign exactly one category to a course. [Updated: Admin cannot publish or activate a course unless a valid category is assigned to it.]
  • Admin can set a fixed price (0.00 for free).
  • New courses default to Draft status.

US 06 – Admin Lesson Management

Priority: Must Have Primary Microservice: Catalog Service

Acceptance Criteria

  • As an admin, I want to manage lessons within a course, so that I can build the educational content.
  • Admin can create a text-based lesson (Title, Text Content) under a course.
  • Admin can edit lesson content.
  • Admin can delete a lesson.

US 07 – Admin Course Lifecycle Management

Priority: Must Have Primary Microservice: Catalog Service

Acceptance Criteria

  • As an admin, I want to toggle a course's status between Draft, Active, and Inactive, so that I can control its public availability.
  • Admin can change a Draft course to Active.
  • Admin can change an Active course to Inactive.
  • Inactive courses immediately disappear from the public catalog.
  • Status changes do not affect existing enrolled users' access to the course content.

US 08 – Browse and Search Catalog

Priority: Must Have Primary Microservice: Catalog Service

Acceptance Criteria

  • As a user, I want to browse and search the active course catalog, so that I can find courses to learn.
  • System displays only Active courses.
  • List supports pagination (server-side via Spring Pageable). [Implemented]
  • User can filter the list by selecting a specific category. [Partially Implemented � frontend UI filter only; backend does not filter by categoryId]
  • User can search by course title. [Partially Implemented � frontend UI search only; backend does not accept a search parameter]

US 09 – View Course Details

Priority: Must Have Primary Microservice: Catalog Service

Acceptance Criteria

  • As a user, I want to view detailed information about a course, so that I can decide whether to purchase it.
  • System displays course Title, Description, Category, Image, and Price.
  • System displays a read-only list of Lesson titles (syllabus).
  • Displays "Buy Now" button if the user is logged in and not already enrolled.
  • Displays "Already Enrolled" if the user owns the course.

US 10 – Single Course Purchase (Mock Checkout)

Priority: Must Have Primary Microservice: Commerce Service

Acceptance Criteria

  • As a user, I want to purchase a course through a simulated checkout, so that I can gain access to its content.
  • System presents a checkout UI for the single selected course.
  • Duplicate purchase is prevented (UI blocks checkout if already enrolled).
  • User selects a mock payment method and system simulates processing.
  • On success, an Order record and an Enrollment record are created.
  • Failed mock attempts do not create Enrollment records.

US 11 – View Order History

Priority: Must Have Primary Microservice: Commerce Service

Acceptance Criteria

  • As a user, I want to view my past successful purchases, so that I have a record of my transactions.
  • System displays a list of the user's successful orders, including Course Title, Date, and Price paid.
  • Failed mock attempts are NOT shown in this history.

US 12 – My Learning Dashboard

Priority: Must Have Primary Microservice: Enrollment Service

Acceptance Criteria

  • As a user, I want to see a list of all courses I am enrolled in, so that I can resume learning.
  • System displays all courses the user is enrolled in (including inactive courses).
  • System displays the overall progress percentage for each course.

US 13 – Access Course Content

Priority: Must Have Primary Microservice: Enrollment Service

Acceptance Criteria

  • As an enrolled user, I want to read the lessons of a course, so that I can learn the material.
  • User can click a lesson to view its text content.
  • Access is strictly denied (403 or UI redirect) if the user is not enrolled.

US 14 – Track Lesson Progress

Priority: Must Have Primary Microservice: Enrollment Service

Acceptance Criteria

  • As an enrolled user, I want to mark lessons as complete, so that my overall course progress is updated.
  • User can toggle a lesson's completion status (Complete/Incomplete).
  • Toggling status immediately updates the course's overall progress percentage calculation.

US 15 – Admin Dashboard

Priority: Must Have Primary Microservice: All Services

Acceptance Criteria

  • As an admin, I want to view high-level platform metrics, so that I can understand business performance.
  • System displays Total Registered Users.
  • System displays Total Active Courses.
  • System displays Total Enrollments across all courses.
  • System displays Total Revenue (Sum of successful order prices).

Data Persistence Rules

The application shall use the shared MySQL database (coursecart_db) as the permanent storage for all business data.

  • All successful Create, Update, and Delete operations shall be immediately persisted in the database.
  • All View and Search operations shall always retrieve the latest persisted records.
  • Changes performed by one module shall be immediately reflected wherever the same data is consumed.
  • No business data shall be maintained only in frontend memory; frontend LocalStorage is strictly reserved for managing active session state (user info and role).
  • Data shall remain available after browser closure, frontend restart, backend restart, application restart, or system reboot.
  • The database shall always be considered the single source of truth for all business operations.

Commerce & Learning Module

Manages simulated checkout, order history, and access to learning materials.

Features:

  • Simulated Single-Course Checkout
  • Order History Reporting

6. Getting Started

6.1 Setup Steps

  1. Start Consul for service discovery: consul agent -dev
  2. Ensure MySQL is running on port 3306.
  3. Initialize the single database by running the SQL scripts from the database/ folder:
    mysql -u root -p < database/schema.sql
    mysql -u root -p < database/test-data-seed.sql
  4. Start each backend microservice using mvn spring-boot:run in this order: coursecart-api-gateway → coursecart-user-service → coursecart-catalog-service → coursecart-commerce-service → coursecart-enrollment-service.
  5. Start the Angular application: run npm install then ng serve from frontend/coursecart-ui/.
  6. Open http://localhost:4200.

9. Implementation Guidelines

9.1 General Coding Practices

  • Use manual getter/setter methods for all model classes (no Lombok). Prefer constructor injection for dependency management.
  • Implement logic using Lambdas and Streams.
  • Organize code into logical layers (Controller, Service, Repository, DTO, Entity, Configuration, etc.).
  • Use meaningful package names reflecting the domain.
  • Employ Spring Dependency Injection for effective component management.

9.2 Error Handling

  • Handle cases where the user attempts to access resources without authorization.
  • Implement custom exceptions with user-friendly error messages.
  • Use a centralized exception handling mechanism to translate exceptions into appropriate HTTP responses.
  • Use @RestControllerAdvice (GlobalExceptionHandler) to intercept, format, and log all service exceptions.
  • Return meaningful success and error responses with appropriate HTTP status codes.

9.3 DTOs and Mapping

  • Data Transfer Objects (DTOs) must be used for all API request and response payloads.
  • Database Entities shall NEVER be exposed directly through REST APIs.
  • Use ModelMapper (or equivalent) to strictly enforce deep conversions between Entities and DTOs within the Service layer.

9.4 Database Interaction

  • Spring Data JPA Repositories must be used for all database operations and query generation.
  • Configure appropriate database properties and table generation strategies (spring.jpa.hibernate.ddl-auto=none is used here as schema generation is manual).

9.5 API Design

  • All APIs should be mapped with an appropriate base URI representing the resource collection (e.g., /api/courses).
  • Ensure strict isolation of server port numbers for each microservice (e.g., Gateway: 8080, User: 8081, Catalog: 8082, Commerce: 8084, Enrollment: 8083).
  • Use appropriate HTTP methods (GET, POST, PUT, DELETE, PATCH) and let Spring automatically resolve appropriate status codes.

9.6 Microservice Communication

  • Register all microservices with Spring Cloud Consul for dynamic service discovery and health monitoring.
  • Route all frontend and external client requests exclusively through the Spring Cloud Gateway.
  • Use RestTemplate for synchronous inter-service communication via HTTP GET/POST calls.
  • Implement Spring Cloud Circuit Breaker (Resilience4j) for inter-service calls using the following precise configuration:
    • slidingWindowSize: 10 (Evaluates the last 10 calls)
    • failureRateThreshold: 50% (Opens the circuit if 50% of calls fail)
    • waitDurationInOpenState: 60 seconds (Time before transitioning to half-open state)
    • Define appropriate @CircuitBreaker fallback methods to ensure graceful degradation.

9.7 Validation

  • Bean Validation should be used for all user inputs.
  • Custom Validators should be implemented for complex validations.
  • All request parameters must be validated for null or empty values. Return standard Bean Validation error messages.

9.8 Testing

  • Write unit test cases for critical service methods using JUnit and Mockito.
  • Achieve a minimum of 80% code coverage.
  • Test all REST APIs using Postman or Swagger/OpenAPI.
